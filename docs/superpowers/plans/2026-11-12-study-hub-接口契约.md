## 1. `Unit` 模型（冻结）

### 1.1 类型

```js
// 轨道（三条顶层轨）
Unit.track        : "algorithm" | "database" | "ai"
// 单元种类
Unit.kind         : "problem" | "card"
// 内容可信度
Unit.status       : "todo" | "draft" | "verified" | "rejected"
// 做题类型
Unit.difficulty   : "easy" | "medium" | "hard"
// 入口种类
Entry.graded      : "user" | "script"
```

### 1.2 完整字段表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | `string` | ✔ | `<trackCode>:<stem>`，全局唯一（G23） |
| `track` | `"algorithm"\|"database"\|"ai"` | ✔ | 顶层轨 |
| `kind` | `"problem"\|"card"` | ✔ | `problem` = 要写答案；`card` = 读讲解 + 跑 demo + 过断言 |
| `title` | `string` | ✔ | 非空 |
| `statement` | `string` | | 讲解正文（题面 / README+NOTES 拼接） |
| `entry` | `Entry` | ✔ | 见 §1.3 |
| `asserts` | `Assert[]` | ✔ | 断言集，**允许为空数组**（无断言的单元不可判） |
| `topics` | `string[]` | ✔ | 知识点；**允许为空数组**，但为空时该单元不计入知识点掌握度 |
| `difficulty` | `"easy"\|"medium"\|"hard"` | ✔ | 缺省 `medium` |
| `source` | `string` | ✔ | `"leetcode"\|"nowcoder"\|"self"\|"grokking"\|"scaffold"\|"generated"\|"codeforces"\|"unknown"` |
| `status` | `"todo"\|"draft"\|"verified"\|"rejected"` | ✔ | 内容可信度，见 §1.4 |
| `progress` | `"todo"\|"in-progress"\|"done"` | ✔ | **学习进度**（旧 frontmatter 的 `status` 语义），缺省 `todo` |
| `reviewed` | `boolean` | ✔ | 人工抽检结果，缺省 `false` |
| `reviewed_at` | `string` | | `YYYY-MM-DD`，未抽检为 `""` |
| `subtracks` | `string[]` | | 算法轨内部的 4 个子轨（`fundamentals`/`interview`/`advanced`/`engineering`），其它轨恒为 `[]` |
| `related` | `string` | | **可选附加字段**，缺省 `""`。loader C 把 `## 关联` 小节原文整段存进来（§3.3）。loader A / B 恒为 `""`。 |
| `path` | `string` | ✔ | 单元文件在**内容根**里的相对路径。内容根 = learning 仓根或工程仓根（loader A 的工程仓题库也用 `bank/` 前缀，形状一致）。loader B = `scaffold/grokking/<stem>/`；loader C = `units/<track>/<stem>.md` |
| ~~`script`~~ | — | — | **已删除**：断言脚本路径只有一处，就是 `entry.script`。不许在 Unit 顶层再放一份 |

### 1.3 `Entry`

```js
Entry {
  demo      : string   // 可运行演示入口（相对 learning 仓根），可空串
  reference : string   // 参考解法入口（供给流水线校验用），可空串
  graded    : "user" | "script"
  script    : string   // graded === "script" 时必填
  language  : "cpp" | "python" | ""   // 入口语言；"" = 不限（由断言脚本自带）
}
```

### 1.4 `Unit.status` 的判定规则（各 loader 自行实现，但结果必须落在上表取值域）

| loader | 规则 |
|---|---|
| **A**（`learning/bank/*.md` + 工程仓 `bank/*.md`） | **按内容判定，不看 frontmatter 的 `needs_fill` 标志**（该标志在存量里已经过时：51 道 CF 原题的 `needs_fill` 仍是 `true`，但题面与用例其实都齐）。规则：题面为空 → `"todo"`；题面非空、测试用例为空 → `"draft"`；题面非空、测试用例非空 → `"verified"` |
| **B**（`scaffold/grokking/<card>/`） | `README.md` **不存在** → **跳过这张卡**（不产出单元）；`README.md` 在、`main.py` 不在 → `"draft"`（可读不可跑）；`README.md` 与 `main.py` 都在 → `"verified"`。**loader B 只读，永远不写盘**；P4 的 `verify` 通过 loader C 的单元文件改判（见 §1.5） |
| **C**（`units/<track>/*.md`） | 直接读 frontmatter 的 `status` 字段 |

> **为什么 loader A 的存量题可以直接是 `"verified"`：** 判定依据是「题面 + 用例都在」——这两样齐了就能自测，参考解法只是 P4/P5 供给流水线用来反查的**加分项**，不是学习的必要条件。实测（2026-11-12）：`learning/bank/` 的 689 份里 687 份是空骨架（→ `todo`），2 份题面与用例齐备（→ `verified`）；工程仓 `bank/` 的 51 道 CF 原题题面与用例齐备（→ `verified`），但**参考解法一节全空**（那是 P5 要补的欠账）。算法轨因此有 **53 个 verified 单元**，会话队列从 P1 起就有东西可排。
>
> **为什么 loader B 的卡是 `"verified"`：** grokking 的卡是**已出版的教材**（人写的 README/NOTES + 人写的 main.py），不是 LLM 生成物——「不用相信 LLM，用执行器验它」这条铁律针对的是 LLM 产物，不适用于已出版内容。真正没建好的是**断言层**（`unit.asserts` 为空、断言脚本可能还不存在），那是**另一根轴**：P2 判题时若断言脚本缺失，报 `compile_error` 并给中文说明；P4 的 `verify` 通过 loader C 的单元文件把卡改判成 `verified` / `rejected`，**loader C 优先级高于 loader B**（去重顺序 C → A → B），所以 P4 之后卡片状态由 P4 的裁决说了算。
>
> **候选池与 `status` 的关系**（P1 用）：候选池 = `status === "verified"` 且 `progress !== "done"` 的单元 + 已到期待复习的单元（同一单元不重复计数）。`draft` / `rejected` 不进候选池。


### 1.5 loader B 的状态写回契约

P4 的 `verify` 子命令跑通 loader B 卡片的断言脚本后，**写回卡片单元文件**（`learning/units/database/<stem>.md` 等），由 loader C 承载 `status: verified`。loader B 自身**只读**。P4 起，`learning/units/` 成为 DB/AI 两轨的唯一落点，loader B 的 `.assert.py` 由 `tools/supply.js generate` 产出到 `learning/units/<track>/<stem>.assert.py`。

## 2. `Assert` 模型（冻结）

```js
// 四种断言，一种判题路径
Assert =
  | { type: "output",   input?: string, expect: string, cmp: "exact" | "trim" | "json" | "lines" }
  | { type: "exit",     expect: 0 }
  | { type: "contains", text: string }
  | { type: "file",     path: string, expect: string }
```

| 字段 | 语义 |
|---|---|
| `output.input` | 喂给 stdin 的输入。**缺省 `""`**（空 stdin）。末尾自动补 `\n`（非空时）。 |
| `output.cmp` | `exact` = 归一化后精确相等（默认）；`trim` = 只去首尾空白后相等；`json` = 两侧 `JSON.parse` 后深度相等；`lines` = 按行数组比较（逐行归一化后相等，行数须一致）。**缺省 `exact`。** |
| `output.expect` | 期望输出，字符串。 |
| `exit.expect` | 期望退出码，**恒为 `0`**（其它值视为非法断言，判题器报 `wrong_answer` 并在 message 里说明）。 |
| `contains.text` | 期望 stdout（`output` 型的 `expect`）或 stderr **合并后**包含的子串。 |
| `file.path` | 相对**沙箱工作目录**的产物文件路径；**禁止** `..` 与绝对路径，越界即判该断言失败。`file.expect` = 文件内容（字符串），比对规则同 `output.cmp`。 |

**归一化规则（沿用 `core/judge-spec/compare.js` 的 `normalizeText`）**：`\r\n` → `\n`；每行去掉行尾 `[ \t\r]+`；整体 `trim()`。

**`cmp` 四档的确切定义**（P2 的 `judge/asserts.js` 必须逐字照此实现）：

| `cmp` | 判定 |
|---|---|
| `exact` | `normalizeText(actual) === normalizeText(expect)` |
| `trim` | `String(actual).trim() === String(expect).trim()`（**不动行尾空白**） |
| `json` | 两侧 `JSON.parse` 后深度相等（对象键序无关、数组元素序有关）；任一侧解析失败 → 该断言失败，reason「期望是 JSON 但解析失败」 |
| `lines` | 两侧按 `\n` 切行后**行数须一致**，且**逐行** `normalizeText` 后相等 |

`output.input` 非空时，喂给 stdin 的内容是 `input + "\n"`（末尾补一个换行）；为空则喂空 stdin。

### 2.1 负例不是第五种断言（P5 追加，冻结）

算法轨的**负例**（故意写错的参考解法）**不是**第五种断言类型。`Assert` 永远只有上面四种（`output` / `exit` / `contains` / `file`）。

负例是**独立的代码产物**：算法单元的负例落在同目录的 `<stem>.negative.cpp`，用**同一批 `output` 断言**去跑它。「负例被拒绝」的定义见 §10.1。

> **为什么不是断言类型：** 断言描述的是「程序该怎么输出」，负例描述的是「一份代码」。把它塞进 `Assert` 会让 `judge/asserts.js` 多一个分支、多一套语义，而实际要做的只是「用同一批断言再跑一次别的代码」。保持 `Assert` 四型，负例走**文件 + 同一个 judge**，是最省事也最不容易出错的形状。

## 3. 三个 loader 的接口（冻结）

### 3.1 loader A —— `core/unit/loader-a.js`

```js
// 读算法题 md（learning/bank/**/*.md 与工程仓 bank/**/*.md），产出 Unit
parseUnitMarkdown(text: string, opts: { track?: "algorithm", relPath?: string }) : { unit: Unit | null, warnings: string[] }
```

**输入**：`text` = 一个 `.md` 文件全文。

**`opts.relPath`**（P0 补充，与 §3.1 第 11 条配套）：该文件相对**内容根**的路径，形如 `bank/interview/lc-00007.md`。loader A 的 `unit.path` 直接取它——**loader 不自己拼路径**（learning 仓题库与工程仓题库形状一致，都是 `bank/` 前缀）。缺省时 `unit.path` 为 `""`（调用方自己知道来源，但本函数不猜）。
**行为**：
1. 用 `core/bank/parse.js` 的 `parseProblemMarkdown(text)` 解析（**不改这个文件**）。
2. `frontmatter.tracks`（数组）→ `unit.subtracks`；`unit.track = "algorithm"`。
3. `frontmatter.id`（如 `lc-00007`）→ `unit.id = "algo:" + id`。**不写回文件。**
4. `frontmatter.status`（`todo`/`in-progress`/`done`）→ `unit.progress`；不在枚举内 → `"todo"`。
5. `frontmatter.needs_fill` **不参与** status 判定（该标志在存量里已过时，见 §1.4）。
6. `frontmatter.source` → `unit.source`（`codeforces` 等原值；不在白名单时填 `"unknown"`）。
7. `unit.kind = "problem"`；`unit.entry = { demo: "", reference: "", graded: "user", script: "", language: "cpp" }`。
8. `unit.asserts` = 由 `problem.cases` 转换：每条 `{input, expect}` → `{type:"output", input, expect, cmp:"exact"}`。`cases` 带 `tol` 时**丢弃 tol** 并在 `warnings` 里加一句中文（见 §3.1.1）。
9. `unit.topics` = `problem.topics`；`unit.difficulty` = `problem.difficulty`（不在 `easy|medium|hard` 内 → `"medium"`）。
10. `unit.statement` = `problem.statement`。
11. `unit.path` = 相对**内容根**的路径（`bank/<subtrack>/<id>.md`）。
12. `unit.reviewed` / `unit.reviewed_at` = `false` / `""`（算法题库不参与抽检；抽检只针对 P4/P5 新产出的单元）。

**status 判定**（见 §1.4 的 loader A 规则）：题面为空 → `"todo"`；题面非空、用例为空 → `"draft"`；题面非空、用例非空 → `"verified"`。

**返回值**：`unit` 为 `null` 当且仅当解析不出 `id`（此时 `warnings` 里有一句中文说明）。

#### 3.1.1 关于 `tol`（浮点容差）

v1 **不实现**浮点容差。`cases` 里带 `tol` 的用例转成 `output` 断言时 `cmp` 一律为 `"exact"`，`tol` 被丢弃，并在该单元的 `warnings` 里加一句：`"用例 N 带 tol 参数，v1 按精确比对处理"`。理由：现有 `bank/` 下**没有任何一份文件实际带 `tol=`**（已 grep 确认），不值得为它扩断言类型。P5 之后若确有需要，另开一期加 `cmp: "float"` 与 `tol` 字段。

10. `unit.path` = `scaffold/grokking/<stem>/`。
11. `unit.progress = "todo"`；`unit.reviewed = false`；`unit.reviewed_at = ""`。

#### 3.3.1 loader C 的算法轨分支（P5 追加，冻结）

`track: algorithm` 且 `kind: problem` 的单元文件，正文小节的名字与 DB/AI 卡**不一样**：

| 小节 | 内容 | 落到 Unit 的哪个字段 |
|---|---|---|
| `## 题面` | 题面正文 | `unit.statement` |
| `## 测试用例` | markdown 表格（`\| input \| expect \|`） | `unit.asserts`：每行一条 `{ type: "output", input, expect, cmp: "exact" }`（与 §3.1 loader A 同构） |
| `## 参考解法` | 单个 ` ```cpp ` 代码块 | **不进 Unit**（见下） |
| `## 关联` | 补充信息 | `unit.related` |

**loader C 只读 frontmatter 的 `reference:` 路径，不读 `## 参考解法` 的代码块内容**。代码块是**给人看的镜像**；`core/supply/algorithm-verify.js` 负责逐字节比对两者是否一致，不一致 → `rejected`。

| 字段 | 含义 |
|---|---|
| `negative:` | 负例文件路径，相对 learning 仓根，如 `units/algorithm/lc-00007.negative.cpp` |
| `source_id:` | 原始题号（如 `7`），用于回链题库 |
| `url:` | 原题链接 |

> `core/supply/algorithm-verify.js` 需要 `negative:` 时，**自己再读一遍单元文件的 frontmatter**，
> 不依赖 `unit` 对象上有什么字段。

算法轨单元的 `graded` 恒为 `user`（学习者提交代码），`entry.script` 恒为空串，`entry.language` 恒为 `cpp`。

### 3.4 loader 汇总 —— `core/unit/index.js`

```js
// 三个 loader 的统一入口 + 索引缓存
loadUnits(opts: {
  learningRoot: string | null,     // null = 纯本地模式
  localBank: string | null,        // 工程仓本地题库根；null = 不加载
  unitsDir: string | null,         // learning/units 目录；null = 不加载
  grokkingDir: string | null,      // learning/scaffold/grokking；null = 不加载
}) : { units: Unit[], warnings: string[], byId: { [id]: Unit } }
```

**规则**：
- **去重**：同一 `id` 出现多次时，**先到先得**（顺序：loader C → loader A → loader B），并在 `warnings` 里加「单元 id 重复：<id>（保留先出现的）」。
- **顺序**：`units` 数组按 `id` **字符串升序**（字典序）。
- **不抛错**：任何单个文件解析失败只进 `warnings`，不中断整体加载。

**索引缓存**：`loadUnits` 每次调用都重新扫盘（与 `FileProvider.list()` 现有行为一致——它的 index 只缓存路径）。P1 起由 `server/db.js` 的 `units` 表做**持久化缓存**，见 §4。

**追加导出（P0 交付，P1 起复用）**：

```js
// 把 loadUnits 的结果物化进 units 表（整体覆盖语义，与 replaceTopics 一致）
refreshUnitIndex(store: object, opts: {
  learningRoot: string | null,
  localBank: string | null,
  unitsDir: string | null,
  grokkingDir: string | null,
}, preloaded?: { units: Unit[], warnings: string[], byId: object })
  : { count: number, warnings: string[] }
```

`count` = 写入 `units` 表的行数。**不抛错**：任何加载失败只进 `warnings`。P0 在 `server/app.js` 启动时调用一次（把单元索引灌进库），P1 的 `/api/units` 与会话排程都读这张表。

**第三个可选参数 `preloaded`（P0 追加）**：调用方如果已经有 `loadUnits` 的结果，直接传进来，函数就**不再扫盘**。
`server/app.js` 在启动时 `loadUnits` 一次、`refreshUnitIndex` 复用同一份结果，避免启动时扫两遍盘。
不传时行为不变（内部自己调 `loadUnits`）。

### 3.5 断言脚本的落地约定（P0 首批 4 张）

**落点**：`learning/units/database/<stem>.assert.py`（learning 仓，新目录）。
**配套的单元 md**（`learning/units/database/<stem>.md`）**P0 不写**——loader C 的单元文件由 P4 的 `verify` 产出。loader B 见到断言脚本存在即认为该卡可判。

**P0 首批覆盖 4 张卡**（都不依赖 numpy，本机可实跑）：

| 单元 id | 断言脚本 | 断言的结论 |
|---|---|---|
| `db:mvcc` | `learning/units/database/mvcc.assert.py` | 版本链、快照隔离、最终余额 2100、演示跑完 |
| `db:transaction` | `learning/units/database/transaction.assert.py` | 原子性回滚、脏读场景、非重复读场景、四级隔离级别、持久性 |

| `db:sql_fundamentals` | `learning/units/database/sql_fundamentals.assert.py` | 建表与索引、示例数据、SELECT/JOIN/聚合/子查询/索引五段演示 |

**脚本的统一形状**（P0 冻结，P4 生成的脚本照此模板）：

```python
#!/usr/bin/env python3
"""<stem> 卡断言脚本 —— 校验 demo 的关键结论都出现在输出里。

用法：
  1) 直接跑：把本脚本与 demo 的 main.py 放在同一目录（沙箱副本）。
  2) 指定 demo：环境变量 STUDY_HUB_DEMO 指向 demo 的绝对路径。
全部断言通过 → exit 0；任一条不通过 → 打印失败原因并 exit 1。

编码：demo 的 stdout 按**本机 locale** 编码（Windows 中文环境是 GBK，Linux 是 UTF-8），
所以这里抓字节再按 utf-8 → gbk → latin-1 的顺序试解码，不写死编码。
"""

import os
import shutil
import subprocess
import sys
import tempfile

DEMO = os.environ.get("STUDY_HUB_DEMO") or os.path.join(
    os.path.dirname(os.path.abspath(__file__)), "main.py"
)

# (说明, 在 stdout 里必须出现的片段)
CHECKS = [
    ("表已创建", "[[OK]] 表已创建"),
]


def decode(raw):
    """把字节流解成文本：utf-8 → gbk → latin-1 依次试。"""
    for enc in ("utf-8", "gbk"):
        try:
            return raw.decode(enc)
        except UnicodeDecodeError:
            continue
    return raw.decode("utf-8", errors="replace")


def run_demo():
    """把 demo 复制进临时目录再跑。

    为什么要复制：这几个 demo 会在 __file__ 旁边写 .db 文件，而且不能重复跑。
    复制进临时目录，既保证每次都是干净环境，也保证 .db 不落进 learning 仓。
    """
    if not os.path.exists(DEMO):
        return None, "找不到 demo：" + DEMO
    sandbox = tempfile.mkdtemp(prefix="study-hub-assert-")
    try:
        target = os.path.join(sandbox, os.path.basename(DEMO))
        shutil.copy2(DEMO, target)
        proc = subprocess.run(
            [sys.executable, target],
            capture_output=True,
            timeout=180,
        )
        return proc, None
    finally:
        shutil.rmtree(sandbox, ignore_errors=True)


def main():
    proc, err = run_demo()
    if err is not None:
        print(err)
        return 1
    out = decode(proc.stdout)
    failed = []
    for name, needle in CHECKS:
        if needle not in out:
            failed.append(name + "（缺少：" + needle + "）")
    if proc.returncode != 0:
        failed.append("demo 退出码非 0：" + str(proc.returncode))
        failed.append("demo 的 stderr 末尾：" + decode(proc.stderr)[-500:])
    if failed:
        for item in failed:
            print("断言失败：" + item)
        return 1
    print("全部断言通过（%d 条）" % len(CHECKS))
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

**三条硬性约定**：

1. **必须用 `subprocess` 跑，不能 `import`。** `mvcc` / `transaction` / `index_design` / `sql_fundamentals`
   四个 demo 都会在 `__file__` 旁边写 `.db` 文件（G18：沙箱隔离靠的就是把 demo 复制进临时目录再跑）。
   用 `subprocess` 跑，`__file__` 就是沙箱里的路径，`.db` 落在沙箱里，不污染 learning 仓。
2. **脚本自己把 demo 复制进临时目录再跑。** 这四个 demo **不能重复跑**（第二次会因为表已存在直接报错），
   所以脚本不能就地执行 `DEMO`，必须先复制到 `tempfile.mkdtemp()` 造出的干净目录里跑，
   跑完 `shutil.rmtree(..., ignore_errors=True)` 清掉。
3. **不能写死 `text=True`。** demo 的 stdout 按**本机 locale** 编码：本机是 Windows 中文环境、
   Python 3.11 的 `sys.stdout.encoding == "gbk"`，所以 `text=True` 会用 GBK 解码，
   在 UTF-8 机器上则相反。改成 `capture_output=True`（抓字节）再按 `utf-8 → gbk → latin-1` 依次试解码。

**P0 的验收**：4 个脚本各跑一次，必须 `exit 0`；且 `learning/` 工作树里**不能多出任何 `.db` 文件**（跑之前先 `git status --porcelain` 记基线，跑之后必须一致）。
另外，**必须做变异测试**：把 demo 的结论串改掉，断言脚本必须 `exit 1`——
一个「怎么都通过」的断言脚本等于没有断言。

## 4. SQLite schema 增补（冻结）

P0 在 `server/db.js` 的 `SCHEMA` 数组里**追加**下列语句，并在 `openDb` 之后调用一次 `migrate(db)`。

### 4.1 现有 4 张表的改造（**不重建表**，**P0 只加列、不动数据**）

**P0 的铁律：纯加法。** 既有列一个都不改名、一个都不删、一个都不改语义；数据迁移留给 P1 / P3。

| 表 | P0 加的列 | 语义变更（何时做） |
|---|---|---|
| `attempts` | `unit_id TEXT`（可空）、`track TEXT NOT NULL DEFAULT 'algorithm'`、`assert_total INTEGER NOT NULL DEFAULT 0`、`assert_passed INTEGER NOT NULL DEFAULT 0` | `problem_id` **原样保留**，继续存旧 id。`unit_id` 是新列，P1 起新链路写它。**P1** 做数据迁移：`UPDATE attempts SET unit_id = 'algo:' || problem_id WHERE unit_id IS NULL AND problem_id NOT LIKE '%:%'` |
| `review_cards` | `unit_id TEXT`（可空）、`units_since INTEGER NOT NULL DEFAULT 0` | `problem_id` 原样保留。**P1** 做数据迁移：`UPDATE review_cards SET unit_id = 'algo:' || problem_id WHERE unit_id IS NULL AND problem_id NOT LIKE '%:%'` |
| `topics` | `track TEXT NOT NULL DEFAULT 'algorithm'` | `topics.id` **原样保留**（旧的纯 topic 名）。**P3** 改成复合键 `<track>:<topic>`，迁移放在 P3 |
| `settings` | 不变 | — |

> **为什么 P0 不动数据：** P0 的验收线要求「旧功能全部不回归」（`/api/attempt` 照旧工作）。旧链路写的是 `problem_id`（无前缀），若 P0 就把 `problem_id` 的语义改成存 `Unit.id` 并顺手迁移数据，旧链路与新链路的语义会在同一个列上打架。所以 P0 另开 `unit_id` 新列，**旧列一律不碰**；数据搬迁在 P1（新链路接管时）与 P3（知识点复合键化时）各自做一次，都是幂等的。

> **为什么 `problem_id` 永远不改名：** SQLite 改列名需要重建表 + 搬数据 + 重建索引，在零迁移框架的现状下风险高于收益。列名保留 + 新列并存 + 分期搬迁，是改动面最小、语义最清晰的做法。`server/db.js` 的 SCHEMA 注释里必须写明这一点。


### 4.2 新增 5 张表

```sql
CREATE TABLE IF NOT EXISTS units (
  id         TEXT PRIMARY KEY,
```

## 6. 核心算法接口（冻结）

### 6.1 跨轨配额 —— `core/scheduler/quota.js`

```js
// 分配一次会话的跨轨配额（最大余数法 / Hare quota）
allocateQuota(input: {
  n: number,                                  // 会话长度（单元数）
  tracks: Array<{ track: string, weight: number, due: number, candidates: number }>,
  minPerTrack?: number,                      // 默认 0
}) : {
  quota: { [track: string]: number },        // 每轨配额，和 === n
  demand: { [track: string]: number },       // 需求度
  weights: { [track: string]: number },      // 有效权重 w'
  needMore: boolean,                         // 候选池不足 → true（转供给流水线）
  reasons: string[]                           // 中文说明
}
```

**算法（逐字实现，spec §4.1）**：

```
1. demand[t]  = 1 + min(1, due[t] / 5)
2. w'[t]      = w[t] × demand[t]
3. n[t]       = floor(N × w'[t] / Σw')        最大余数法补齐到 Σn = N
4. 回收       若 C[t] < n[t]，多余配额按 w' 比例分给仍有候选的轨
5. 兜底       若 ΣC = 0 → needMore = true
```

**边界**：
- `Σw' === 0`（所有权重为 0）→ 各轨等分（`floor(N/len)` + 余数按轨道声明顺序补给第一个）。
- `N < tracks.length` → 先按 `minPerTrack`（默认 0）保证每轨至少 0，再按余数法分剩下的。
- 某轨 `candidates === 0` → 该轨配额为 0，其配额按 `w'` 比例分给有候选的轨；若所有轨都没候选 → `needMore = true`，`quota` 各轨为 0，`reasons` 含「没有可学的单元，建议去供给流水线补内容」。

**确定性**：同输入必同输出（不读时钟、不用 `Math.random`）。余数相同时按 `tracks` 数组的**声明顺序**优先。

### 6.2 队列成形 —— `core/scheduler/queue.js`

```js
// 把每轨的候选单元排成一条跨轨交错的队列
buildQueue(input: {
  quota: { [track: string]: number },
  pools: { [track: string]: Unit[] },        // 每轨已排好序的候选
}) : Array<{ unit: Unit, track: string, seq: number }>
```

**规则**：
1. 每轨内部顺序由调用方给（`pools[t]` 已按 §6.5 的优先级排好），本函数**不重排**。
2. 跨轨用 **round-robin 交错**，按轨的配额取数。
3. **连续同轨上限 = 该轨配额的 2 倍**（下限 2）。超限则把该轨的下一个单元推迟。
4. 输出 `seq` 从 **1** 开始连续。

### 6.3 轨内优先级 —— `core/scheduler/prioritize.js`

```js
// 给一轨的候选单元排出优先级顺序（纯函数，不碰 DB）
prioritize(units: Unit[], ctx: {
  dueUnitIds: Set<string>,        // 已到期的单元 id（日期或次数通道）
  currentRoundUnitIds: Set<string>, // 属于当前轮次且未完成的单元 id
  roundOrder: string[],           // 当前轮次里的单元顺序（按题号）
  masteryByUnit: { [unitId: string]: number },
  doneUnitIds: Set<string>,
}) : Unit[]
```

**排序键（从高到低）**：
1. 到期复习的单元（`dueUnitIds`）
2. 当前轮次里未完成的单元（按 `roundOrder` 的下标）
3. 其余新单元（按 `masteryByUnit` 升序——越弱越先；再按 `id` 升序定序）
4. 已完成（`doneUnitIds`）的单元**排到最后**（仍可被选，因为可能需要重练）

**确定性**：同输入必同输出。

## 7. 判题契约增补（P2）

### 7.1 新增导出 —— `judge/asserts.js`

```js
// 断言校验器：跑完进程后逐条校验断言集
validateAsserts(asserts: Assert[], run: {
  stdout: string, stderr: string, exitCode: number | null,
  timedOut: boolean, artifacts: { [relPath: string]: string }   // 沙箱目录下的产物文件内容
}) : { passed: number, total: number, failures: Array<{ index: number, type: string, reason: string }> }
```

**规则**：
- `exit` 型：`exitCode === 0` 才过；非 0 → 失败，reason「期望退出码 0，实际 <code>」。
- `output` 型：按 `cmp` 规则比对 `stdout` 与 `expect`。
- `contains` 型：在 `stdout + stderr` 合并串里找 `text`。
- `file` 型：读 `artifacts[path]`；`path` 含 `..` 或以 `/` 开头 → 直接失败（reason「产物路径越界：<path>」）；文件不存在 → 失败（reason「产物文件不存在：<path>」）。
- `total` = 断言条数；`passed` = 通过条数。

### 7.2 `judge/runner.js` 追加 —— 单路径判题

```js
// 追加导出（不改 judge / parseCompilerError / VERDICTS 等既有导出）
judgeUnit(params: {
  unit: Unit,                    // 含 asserts / entry
  code: string,                  // kind === "problem" 时用户提交的代码；kind === "card" 时空串
  language?: string,
  timeoutMs?: number,
  toolchain?: object,
  sandbox?: object,              // 可选：外部准备好的沙箱（供给流水线校验用）
}) : Promise<{
  verdict: string,               // 五类之一（G20）
  passedCases: number,           // = 通过的断言数
  totalCases: number,            // = 断言总数
  durationMs: number,
  failedCase: { index: number, type: string, reason: string } | null,
  message: string,
  compilerOutput: string,
  stdout: string,                // 新增：供 UI 展示 demo 输出
}>
```

**行为**：
- `unit.entry.graded === "user"` → 走 `judge()` 的老路径（编译 / 写 `main.cpp` / 写 `main.py` / 跑用例），但**断言集换成 `unit.asserts`**（而不是 `problem.cases`）。
- `unit.entry.graded === "script"` → **执行 `unit.entry.script` 指向的断言脚本**（相对 learning 仓根），把断言脚本**复制到沙箱**再跑（G18：绝不污染 learning 仓）。断言脚本自身内部做断言并 `sys.exit(0)` 表示通过；本函数再对 `unit.asserts` 做二次校验（`exit: 0` + 若干 `contains`）。
- **verdict 映射**：
  - 进程超时 → `timeout`
  - 编译失败 / Python 语法错 → `compile_error`
  - 进程非零退出且不是断言不匹配 → `runtime_error`
  - 进程正常退出但断言未全过 → `wrong_answer`
  - 断言全过 → `pass`
- **`kind: card` 的脚本失败**归 `wrong_answer`（断言没通过）或 `runtime_error`（脚本自己崩了）——与 `kind: problem` 共用同一套判定（G20）。

## 10. 供给流水线 CLI 契约（P4 / P5）

```
node tools/supply.js <command> [options]
```

| 子命令 | 选项 | 行为 | 退出码 |
|---|---|---|---|
| `plan` | `--track <t>` | 扫描三轨，输出缺口清单（缺断言 / 缺讲解 / 缺用例 / 缺解法），输出到 stdout 与 `learning/units/<track>/plan.json` | 0 |
| `generate` | `--track <t> --limit <n>` | 调 LLM 产出单元文件 + 断言脚本，落 `learning/units/<track>/`，`status: draft` | 0（LLM 关掉时 503 语义 → 退出码 2 + 中文提示） |
| `verify` | `--all` \| `--track <t>` \| `--unit <id>` | 跑执行器反向校验：`draft → verified` 或 `draft → rejected` | 0（有不通过项也退出 0，**结果打在输出里**） |
| `review` | `--sample <n>` \| `--track <t>` | 抽检：打印待抽检单元（含题面与断言），人点通过 / 打回 → 写回 frontmatter | 0 |
| `report` | `--track <t>` | 打印每轨的 `todo/draft/verified/rejected` 计数与欠账 | 0 |

**`verify` 的判定规则（P4 必须照此实现）**：

| 轨 | 校验动作 | 通过条件 |
|---|---|---|
| `algorithm`（`kind: problem`） | 跑 `entry.reference` 指向的参考解法 × 全部断言 | 全过 → `verified` |
| `algorithm` | 跑负例（若有 `negative` 断言） | 负例必须被拒 |
| `database` / `ai`（`kind: card`） | 跑 `entry.script` 断言脚本 | 脚本 `exit 0` 且 `unit.asserts` 全过 → `verified` |
| `database` / `ai` | **变异测试**：把被测 demo 的一个分支改坏，重跑断言脚本 | 断言脚本**必须失败**；若仍通过 → `rejected`（理由：「变异测试未捕获，断言无效」） |

**变异测试的实现约束**：只允许改**沙箱副本**里的 demo 文件，**绝不改 learning 仓里的文件**（G18）。变异手法三选一（按顺序尝试，第一个能改坏的就用）：
1. 把 demo 里第一条 `assert ` 语句改成 `assert False`
2. 把 demo 里第一条 `if ...:` 的条件改成 `if False:`
3. 把 demo 里第一条 `return ` 语句改成 `return None`

找不到任何可改点 → 该单元标记 `rejected`，理由「找不到可变异点，无法验证断言有效性」。

### 10.1 算法轨的批量补题（P5 追加，冻结）

`generate` 在算法轨上**一次 LLM 调用产四件套**（题面 / 用例 / 参考解法 / 负例），落 `learning/units/algorithm/`：

| 产物 | 路径（相对 learning 仓根） | 说明 |
|---|---|---|
| 单元文件 | `units/algorithm/<stem>.md` | loader C 读它 |
| 参考解法 | `units/algorithm/<stem>.reference.cpp` | frontmatter `reference:` 指向它，判题器编译它 |
| 负例 | `units/algorithm/<stem>.negative.cpp` | frontmatter `negative:` 指向它，质检专用 |

`<stem>.negative.cpp` 是**冻结的命名约定**：与单元 md 同目录、同 stem。**负例的内容绝不进单元 md**——学习者只看得到正确解法。

**P5 在五个子命令上的选项**（`--track algorithm` 时生效）：

| 选项 | 适用子命令 | 行为 |
|---|---|---|
| `--batch` | `generate` | 批量模式：一次跑一批（默认行为，`--batch` 是显式写法） |
| `--limit <n>` | `generate` / `plan` | 本次最多处理 n 个题 |
| `--resume` | `generate` | 断点续跑：跳过已 `verified` 与已 `rejected` 的题；只重跑 `failed` 的题 |
| `--retry-rejected` | `generate` | 与 `--resume` 同用：把已 `rejected` 的题也重新放进本轮 |
| `--dry-run` | `generate` | 只算计划、只打清单，**不调 LLM、不写文件** |
| `--session <batchId>` | `generate` | 批次号，默认 `batch-<YYYYMMDD>`；记账与续跑都用它 |
| `--unit <id>` | `verify` | 只校验这一个单元（契约原有的选项） |

**`generate` 的退出码**：`0` 成功（含「跑完了但有题被拒」——结果打在输出里）；`2` = LLM 关掉（503 语义，输出中文提示）；`1` = 参数错 / learning 仓路径解析不出来。

**`verify` 在算法轨上的判定规则**（`kind: problem` 且 `track: algorithm`）：

| 步 | 动作 | 通过条件 | 不过时的单元结论 |
|---|---|---|---|
| 1 | 跑 `entry.reference` 指向的参考解法 × **全部**用例 | `verdict === "pass"` | `rejected`，理由写明是 `wrong_answer` / `timeout` / `runtime_error` / `compile_error` 里的哪一个 |
| 2 | 跑负例（`negative:` 指向的文件；**没有负例文件就是不合格**） | `verdict ∈ {wrong_answer, runtime_error, timeout}` | `rejected` |

**负例的五种情形各自的结论**（冻结）：

| 负例的 verdict | 算「被拒绝」吗 | 单元结论 | 理由文案 |
|---|---|---|---|
| `wrong_answer` | ✅ 算 | 参考解法也全过 → `verified` | 「负例被拒绝（wrong_answer）」 |
| `runtime_error` | ✅ 算 | 同上 | 「负例被拒绝（runtime_error）」 |
| `timeout` | ✅ 算 | 同上 | 「负例被拒绝（timeout）」 |
| `pass` | ❌ 不算 | `rejected` | 「负例竟然全部通过，说明测试用例太弱，挡不住错解」 |
| `compile_error` | ❌ 不算 | `rejected` | 「负例编译失败，负例本身无效」 |

**负例被拒 = 质检通过**（负例**没**被拒 = 质检失败）。单元级结论词只有 `verified` / `rejected`；`pass` / `wrong_answer` / `timeout` / `compile_error` / `runtime_error` 是**单次执行**的结论（G20 冻结的五类，不增不改）。

**批次状态落在 `settings` 表**（键名见 §5），**不新建数据表**。`--resume` 靠 `supply.batch.item.algo.<stem>` 判重：**同一个批次重跑不重复花钱**。

## 14. `core/track/tracks.js`（P0 新建，冻结）

```js
module.exports = {
  TRACKS: [
    { code: "algorithm", label: "算法", idPrefix: "algo", subtracks: ["fundamentals", "interview", "advanced", "engineering"], weight: 0.4, enabled: true },
    { code: "database",  label: "数据库", idPrefix: "db", subtracks: [], weight: 0.3, enabled: true },
    { code: "ai",        label: "AI", idPrefix: "ai", subtracks: [], weight: 0.3, enabled: true }
  ],
  TRACK_CODES: ["algorithm", "database", "ai"],
  GROKKING_DB_CARDS: [...],   // 16 个 grokking 数据库卡的目录名
  GROKKING_AI_CARDS: [...],   // 13 个 grokking AI 卡的目录名
  trackOf(code: string) : object | null,
  trackOfIdPrefix(prefix: string) : object | null,
  labelOf(code: string) : string,          // 未知 code 返回 "未知轨道"
  trackOfGrokkingCard(stem: string) : string | null   // "database" | "ai" | null
}
```

**权重与开关的运行期覆盖**：`settings` 表的 `track.weight.<code>` / `track.enabled.<code>` 优先于此处的默认值。

### 14.1 grokking 卡的轨道归属（**实测清单，冻结**）

`learning/scaffold/grokking/` 下共 **88** 个卡目录，其中 **59** 个带 `main.py`（其余 29 个是纯算法 / C++ 并发卡，不属本轮三轨范围）。

**数据库轨（16 个）**：
`anti_patterns`、`backup_recovery`、`cache_strategy`、`cap_theorem`、`clustering`、`index_design`、`lock_manager`、`mvcc`、`newsql`、`normalization`、`nosql`、`query_optimization`、`replication`、`sharding`、`sql_fundamentals`、`transaction`

**AI 轨（13 个）**：
`cnn`、`decision_tree`、`dimensionality_reduction`、`gradient_boosting`、`linear_regression`、`logistic_regression`、`ml_fundamentals`、`neural_network`、`nlp`、`random_forest`、`recommendation`、`rnn`、`svm`

**numpy 依赖**：`clustering` 与全部 13 个 AI 卡 `import numpy`；其余 15 个数据库卡**不需要 numpy**。
→ 缺 numpy 时：数据库轨仍可用（15 个卡可跑），AI 轨标「环境缺失」并跳过（spec §1.6 / §9）。

> **数字订正**：设计文档附录 #15 写的是「28 张 Python 卡（db 14 + ml 14）」，实测是 **29 张（db 16 + ai 13）**。以本节清单为准。

### 14.2 `subtracks` 的来源

算法轨的 `subtracks` 来自存量 frontmatter 的 `tracks` 字段：`learning/bank/{fundamentals,interview,advanced}` 与工程仓 `bank/{fundamentals,interview,advanced,engineering}`。**`tracks` 是算法轨的内部子轨，不是三条顶层轨**——顶层轨恒为 `algorithm`。

## 15. 写计划时的硬性要求

每一份 P0–P5 计划必须遵守：

1. **不许另起炉灶**：模块名、导出签名、路由路径、响应字段、DB 列名、settings 键 —— 一律照本文档。发现本文档缺东西，**先改本文档**再写代码。
2. **每个任务一个可独立验证的交付物**，任务末尾 `git add` + `git commit` + `git push`（G27）。
3. **测试先行**：每个任务先写失败测试 → 跑一次确认失败 → 实现 → 跑一次确认通过 → 提交。
4. **不许占位符**："TBD" / "TODO" / "补合适的错误处理" / "照 Task N 写" 一律不许出现。每个步骤都要有真代码、真命令、真预期输出。
5. **中文文案**：所有面向用户的字符串在计划里就要写死中文原文，不许留"用中文提示"。
6. **既有测试不许无理由变红**：如果 P1/P2/P3 的改造会让旧测试失败，**在同一个任务里同步改旧测试**并说明为什么改。
7. **计划文件路径**：`docs/superpowers/plans/2026-11-12-study-hub-P<n>-<名字>.md`（父仓）。
